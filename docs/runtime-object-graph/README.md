# 运行时对象图复制

对象图复制用于保留一组对象的当前数据，以及这些对象之间的引用关系。例如，玩家对象引用牌堆，牌堆引用卡牌，卡牌又引用所属玩家；这些对象和引用共同组成一个“对象图”。框架从调用方传入的对象出发，沿字段引用处理相关对象，得到供预测使用的数据。

本文说明复制基础设施的架构，以及各接入的用途和策略制定原则。具体 API、类型清单和字段处理规则见 [ObjectGraph 源码](../../RandomForeseerCode/ObjectGraph/)及其注释。

## 核心概念

调用 `Copy(source)` 时传入的起始对象称为“根”。一次复制会话可以先后复制多个根：例如分别传入两个玩家，复制它们各自的牌堆和卡牌。这里的“捕获”指调用方为取得这一组数据而完成的整次复制会话。

复制会话使用 `PredictionObjectScope`（下文简称 scope）记录原对象与副本的对应关系。这种对应关系按对象是否为同一个实例判断。例如，两个玩家都引用同一个战斗对象时，使用同一个 scope 复制它们，得到的两个玩家副本也会引用同一个战斗副本。对象之间的循环引用也通过这份对应关系保留。

Policy 是调用方提供的复制策略，决定图中哪些对象需要独立副本、哪些继续使用原对象，以及哪些字段应清空。不同用途可以使用不同的 policy；复制机制和对象对应关系由框架统一维护。

## 组件与复制流程

| 组件 | 职责 |
| --- | --- |
| `PredictionGraphCopier` | 从根开始遍历字段，执行 policy 选出的处理方式，并记录出错对象的访问路径。 |
| `PredictionObjectScope` | 记录原对象与副本的对应关系，供多个根和循环引用复用。 |
| `GraphCopyPolicy` | 保存有先后顺序的处理规则，并缓存每种类型的复制计划。 |
| `Metadata` | 读取类型、字段及继承关系等信息，供规则判断和计划生成使用。 |
| `Plans` | 根据类型及 policy 确定各字段的处理方式，形成“类型计划”，并生成相应的字段访问代码。 |
| `Copiers` | 执行普通对象、集合和回调等类型各自的复制操作。 |

对于选择复制的引用对象，框架先创建副本并记入 scope，再处理其字段。递归访问同一原对象时直接取得已登记的副本，因此可以保留循环引用。框架以已有字段数据为基础完成复制；模型初始化、派生属性计算和玩法流程由各自的调用方负责。

每次捕获建立一组 scope 和 copier，所有根共用这组对象。捕获按同步、单线程方式执行，调用方在所有根复制完成后再使用或修改结果，并在此之前保持源数据和 policy 使用的上下文稳定。如果中途失败，整个 scope 随之失效，调用方应放弃本次捕获。捕获结束后释放 scope 会清理对应关系，返回的副本由持有它们的调用方继续管理。

Policy 可以跨次捕获复用。类型计划及生成代码缓存在 policy 中；例如多次复制同一种卡牌时，可以复用已经确定的字段处理方式。依赖具体实例的判断在复制时读取本次调用的上下文，例如判断某张卡是否属于本次需要保存的模型。

## 策略如何确定处理方式

接入方先确定结果将用于什么场景、需要保留哪个时点的数据，以及后续会读取或修改哪些对象，再为对象和字段选择处理方式：

| 处理方式 | 含义与适用情形 |
| --- | --- |
| 复制 | 创建独立副本，并继续处理其中的数据。适用于需要独立修改或保留当前内容的对象。 |
| 共享 | 继续引用原对象。适用于调用方接受外部变化、并按约定使用的对象；双方都会观察到同一对象的修改。 |
| 保留字段 | 保留源字段的值。引用字段继续指向原对象，适用于已确认可以共享的字段。 |
| 重置字段 | 将副本中的字段设为默认值，例如将引用设为 `null`。适用于结果用途之外的临时执行对象。 |
| 拒绝 | 抛出异常并结束本次捕获。适用于当前策略尚无法可靠处理的对象。 |

字段规则根据字段声明的类型及字段信息选择行为；引用规则还可以根据对象的实际类型及本次调用的上下文判断。例如，声明为 `object` 的字段可以装入纹理，引用规则在访问该值时仍能识别出纹理类型。规则按顺序取第一个匹配项，接入提供的规则排在框架默认规则之前。

共享策略需要结合后续用途审查：只读使用的显示资源可以保留原引用，准备独立修改的模型数据则需要副本。临时执行字段重置后，结果保留用于展示或计算的数据；后续预测从调用方选定的入口开始。具体接入按需启用通用规则，类型清单、字段例外和规则顺序维护在对应 policy 源码中。

副本调用的方法仍执行原来的代码。例如，方法通过 `CombatManager.Instance` 查询战斗历史时，访问的仍是真实游戏的历史。要在副本上运行玩法逻辑，预测层还需提供对应的数据访问和执行入口，处理全局服务、界面操作、存档及网络调用。

## 具体接入

### 模型快照

预测历史在抽牌、生成卡牌或生成药水时，保存该模型当时的数据，供之后展示预览。这种面向特定时点和用途的数据副本称为“模型快照”。当前由 `CombatPredictionHistory` 调用 [`ModelSnapshotCopier`](../../RandomForeseerCode/ObjectGraph/ModelSnapshotCopier.cs) 完成捕获，正式战斗预测逻辑由 InCombat simulator 执行。

每次捕获以一张卡牌或一瓶药水为根，建立独立的 scope 和 copier，复用模型快照 policy。Policy 根据本次传入的模型识别需要复制的对象；卡牌的附魔、灾厄等附件随卡牌一起保存，玩家、战斗和运行状态继续保留原引用。

这个接入以展示所需的数据为策略依据：复制模型自身的数据，保留只读显示资源，清理实时节点和临时执行状态。例如，卡牌快照保存当时的费用和附魔数据，卡图则可以继续引用共享纹理。原 Mod 更新该纹理后，预览也会显示更新后的图像。通过所属玩家等外部引用计算的属性，仍会读取相应对象的当前数据。

### 战斗数据图

战斗数据图用于研究和验证更大范围的战斗状态复制，包括玩家、牌堆、模型和随机数生成器（RNG）。当前接入通过战斗数据回归用例验证，使用 [`CombatGraphPolicy`](../../RandomForeseerCode/InCombat/ObjectGraph/CombatGraphPolicy.cs) 确定处理规则。

一次捕获可以传入多个玩家或战斗对象作为根，它们共用 scope 和 copier。沿字段引用能够访问到的对象称为“可达对象”；这些对象使用同一份对应关系完成复制，使卡牌的所属玩家、牌堆中的卡牌及 RNG 引用在副本中继续对应。

这个接入以独立演变战斗状态为策略依据：玩家、牌堆、RNG 以及沿引用访问到的本局游戏状态（RunState）都需要相应副本。原版 canonical 模型代表共享的模型定义，mutable 模型代表运行中的可变实例，policy 分别按定义共享和实例复制处理。遇到当前策略无法处理的资源时结束捕获，由接入方补充合适的处理方式。副本上的玩法执行由预测层组织，包括数据访问，以及对真实游戏或外部系统的修改操作。

## 验证与维护

基础设施测试检查多个字段是否仍指向同一副本、循环引用是否保留，以及复制后修改副本时源对象是否保持原状。接入测试检查各场景选定的复制和共享范围。测试入口位于 `tests/RandomForeseer.Tests/ObjectGraph/`，战斗数据图用例位于其 `Combat/` 子目录；运行方式和共享测试规则见[本地回归测试](../testing.md)。
